# 测试策略

测试的目标是保护用户可观察行为和跨层契约，不是固定页面内部的每一个 Widget 层级。新增测试应选择能够以最低成本证明风险的层级。

## 优先覆盖的契约

- 网络与会话：鉴权、刷新令牌、会话持久化、错误映射和并发请求。
- API 与 DTO：HTTP 方法、路径、查询参数、请求体、响应映射和后端错误。
- Provider：初始加载、刷新、分页、筛选、重试、并发、失败恢复、事件广播和销毁后的异步回写。
- 路由：登录重定向、平台入口、深链、参数解析、返回目标和页面接线。
- 共享组件：公开回调、禁用状态、键盘/鼠标/触摸交互、可访问语义和平台差异。

## 页面测试边界

Widget 测试只在低层测试无法证明时添加，例如：

- 表单确实把输入提交给正确的 Provider；
- 关键动作正确打开确认流程并反馈结果；
- 平台专属行为依赖真实 Widget 树；
- 已发生且无法由 API、Provider、路由或共享组件测试覆盖的回归。

不要因为桌面和移动页面都存在就重复测试完全相同的状态机；页面测试关注接线，Provider 测试关注状态转换。

## 断言原则

优先断言：

- 请求是否正确；
- 状态和错误是否可恢复；
- 导航目标和返回行为是否正确；
- 用户能看到的内容、反馈和可访问语义是否出现。

通常不要断言：

- 无业务意义的私有 Widget 层级或装饰组件数量；
- 精确字号、间距、百分比高度和布局算法；
- 已由更低层测试覆盖的同一分支；
- 通过扫描生产源码字符串来证明实现方式。

主题裸值守卫集中在 `test/theme/theme_source_guard_test.dart`，业务组件测试不要重复实现源码扫描。

## 测试前检查

1. 失败会造成什么真实用户或数据风险？
2. 能否用纯 Dart/Provider/API 测试验证？
3. 仓库中是否已经有覆盖同一行为的测试？
4. 测试是否依赖公开、稳定的契约？
5. 只改变 UI 结构而不改变用户行为时，测试是否仍然应该通过？

## 运行方式

- 修改单个模块：直接运行对应测试文件或目录。
- 提交前：运行 `./scripts/test.sh`；该脚本会根据当前 `test/` 内容生成临时 bundle。
- 修改生产代码：运行 `flutter analyze --no-fatal-infos --no-fatal-warnings`。
- 修改路由或 Riverpod 注解：先运行 build_runner，再运行相关测试。
